Glossary

Key terms and concepts used across the apps on this site.

From Idea to Live Site — The Full Journey

This section walks through the entire lifecycle of a change — from giving a direction to seeing it live on the internet. Every term below is part of the real process used to build and maintain this site.

1. The Idea
Everything starts with a person deciding what to build or change. In this project the user describes what they want in plain language to an AI coding assistant called Claude Code. The request could be anything: "add a glossary page," "fix the scoring bug," or "build a new game."
Claude Code
An AI assistant that reads, writes, and modifies code based on natural-language instructions. It works directly inside the project's repository — reading files, creating new ones, running commands, and committing changes. It is the primary developer of this site.
2. The Repository (Repo)
A folder that contains every file in the project together with the complete history of every change ever made. This site lives in a single Git repository hosted on GitHub. The repo is the single source of truth — if it's not in the repo, it doesn't exist.
Git
The version-control system that powers the repository. Git tracks every change as a series of snapshots, lets multiple lines of work happen in parallel, and makes it trivial to undo mistakes. It runs locally on the developer's machine (or in Claude Code's environment) and syncs with GitHub.
Source Code
The human-readable (and AI-readable) files that make up the apps: TypeScript, HTML, CSS, JSON data files, configuration, and more. Source code is what gets edited; it later gets transformed into the files the browser actually runs.
3. Working on a Branch
Before making changes, a new branch is created — a parallel copy of the codebase. This keeps work-in-progress isolated from the stable main branch. Branches are cheap and disposable; you can have many at once. The naming often hints at the purpose, e.g. claude/add-glossary-page.
4. Writing & Editing Code
Claude Code (or a human developer) creates and modifies files in the repository. This can mean writing new components, editing HTML, updating configuration, or adding data files. The developer can see what changed at any time using git diff, which highlights every added, removed, or modified line.
5. Committing Changes
A commit is a saved snapshot of the project at a moment in time. Each commit bundles a set of related changes with a message explaining what changed and why. Commits are permanent and form the project's history — you can always go back to any previous commit.
Staging (git add)
Before committing, you choose exactly which changed files to include. This is called staging. It lets you make a clean, focused commit even if you've changed many files — you only stage the ones relevant to the current task.
6. Pushing to GitHub
Pushing uploads your local commits to the remote repository on GitHub so others (and automation) can see them. Until you push, your work only exists on your machine. Pushing makes the branch and its commits available to the whole project.
GitHub
A platform for hosting Git repositories online. It layers collaboration features — pull requests, issues, code review, actions — on top of Git. Think of it as the project's home base on the internet.
7. Opening a Pull Request (PR)
A pull request is a formal proposal to merge your branch into main. It shows every change side-by-side (the "diff"), lets reviewers leave comments on specific lines, and serves as a record of why the change was made. PRs are the checkpoint between "work done" and "work shipped."
Code Review
The process of examining someone's proposed changes before they go live. Reviewers can approve, request changes, or ask questions directly on the pull request. It catches bugs, improves quality, and shares knowledge. In this project the user reviews what Claude Code wrote.
Diff
A line-by-line comparison showing exactly what was added (green), removed (red), or changed in a set of commits. Diffs are the core visual of pull requests and code review — they answer the question "what's different?"
8. Merging
Once a pull request is approved, it gets merged — its commits are folded into the main branch. After merging, the feature branch is typically deleted since its work now lives in main.
Merge Conflict
When two branches change the same lines in different ways, Git can't automatically combine them. This is a merge conflict. A human (or Claude Code) has to manually decide which version to keep. Conflicts are normal and usually easy to resolve.
9. Automated Build & Deploy (CI/CD)
The moment code lands on main, GitHub Actions kicks in automatically. A workflow file (stored in the repo at .github/workflows/deploy.yml) defines the steps: install dependencies, build each React app, assemble the full site, and deploy it. No human intervention needed.
GitHub Actions
GitHub's built-in automation system. It runs workflows in response to events (like a push to main). Each workflow is a series of steps that run in a fresh virtual machine. This project's action builds three React apps and assembles them alongside the static apps.
Workflow
A YAML configuration file that tells GitHub Actions what to do. This project's workflow installs Node.js, runs npm ci and npm run build for each React app, copies the static apps, and uploads the result as a deployable artifact.
Build
The process of transforming source code into optimized files a browser can run. Vite compiles TypeScript, bundles JavaScript modules, processes CSS, and outputs a dist/ folder. The static apps (Calendar Puzzle, Pokémon) skip this step — they're already browser-ready.
npm (Node Package Manager)
The tool that installs third-party libraries (React, Vite, Tailwind, etc.) that the apps depend on. npm ci installs exact versions from a lock file; npm run build triggers the build process.
Dependencies
External libraries the project relies on. Listed in each app's package.json file with exact versions locked in package-lock.json. Examples: React for UI rendering, Vite for building, Tailwind for styling.
Artifact
The final output of the build step — a bundle of files ready to be served. The deploy workflow assembles all apps into a single _site/ folder, which becomes the artifact uploaded to GitHub Pages.
10. Live on GitHub Pages
GitHub Pages serves the artifact as a real website at msvante.github.io/apps/. Within minutes of merging a PR, the changes are live and anyone with the URL can see them. The cycle is complete: idea → code → review → merge → build → deploy → live.
Deploy
The final step: publishing the built site so it's accessible on the internet. In this project, GitHub Actions uploads the _site/ folder to GitHub Pages, which serves it as a static website. No servers to manage — it just works.

Other Useful Terms

Issue
A tracked task, bug report, or feature request on GitHub. Issues are how work gets planned and discussed before any code is written. They can be referenced from commits and pull requests to link the "why" to the "what."
Clone
Downloading a full copy of a repository (including its entire history) to your local machine. This is the first step when starting to work on a project. Claude Code operates on a cloned copy of this repo.
Fork
A personal copy of someone else's repository on GitHub. Forks let you experiment freely without affecting the original project. Changes can be proposed back via pull request.
Main Branch
The primary branch of the repository, called main. It represents the current "official" state of the project. Code only reaches main through reviewed and merged pull requests. Pushes to main trigger the deploy.
Remote / Origin
The version of the repository that lives on GitHub's servers (as opposed to your local copy). By convention it's called origin. Pushing sends your commits to the remote; pulling fetches changes from it.
CLAUDE.md
A special markdown file in the repository that gives instructions to Claude Code. It describes the project structure, conventions, and rules the AI should follow. Think of it as a briefing document for the AI developer.
CI/CD (Continuous Integration / Continuous Deployment)
The overall practice of automating the path from code change to live site. "Continuous Integration" means changes are automatically built and tested. "Continuous Deployment" means they're automatically published. This project does both via GitHub Actions.
Environment
The context in which code runs. The development environment is where code is written and tested. The production environment is the live site users visit. GitHub Actions provides the build environment — a temporary machine that compiles the code.

General Tech

GitHub Pages
The free hosting service from GitHub that serves this site. Every push to the main branch triggers a deploy that builds and publishes all apps.
Vite
A fast build tool used by the React-based apps (Lineup Guesser, Bracket City, Hangman). It bundles source code into optimized files for the browser.
React
A JavaScript UI library. Most apps on this site are built with React and TypeScript, using components and hooks to manage game state.
TypeScript
A typed superset of JavaScript. Adds type annotations to catch errors before the code runs. Used by the React-based apps.
Tailwind CSS
A utility-first CSS framework that lets you style elements with short class names (e.g. bg-blue-500) directly in HTML. Used by some of the React apps.
Static App
An app built with plain HTML, CSS, and JavaScript — no build step required. The Calendar Puzzle and Pokémon games are static apps.

Game Concepts

Hint all games
An optional clue you can request during a game. Hints make the puzzle easier but usually cost you points or reduce your score.
Streak
A count of consecutive correct answers. Used in games like Who's That Pokémon to track how many you get right in a row.
Daily Puzzle
A puzzle that changes once per day so every player gets the same challenge. Used by the Calendar Puzzle and Bracket City.
Fuzzy Matching
A forgiving way to check answers. Small typos and missing accents are tolerated using techniques like Levenshtein distance. Used in Lineup Guesser.
Levenshtein Distance
A measure of how different two strings are, counting the minimum number of single-character edits needed to turn one into the other. Powers the fuzzy matching in Lineup Guesser.

App-Specific Terms

Formation Lineup Guesser
The tactical arrangement of players on the pitch (e.g. 4-3-3, 3-5-2). Each match uses a real formation from the Premier League.
Bracket / Nested Bracket Bracket City
A clue wrapped in square brackets. Brackets can contain other brackets, and inner brackets must be solved before the outer one becomes solvable.
Hidden Word Hangman
The single word in a news headline that you need to guess letter by letter. The rest of the headline is shown in gray as context.
Silhouette Pokémon
A blacked-out outline of a Pokémon. Your job is to identify which Pokémon it is from the shape alone.
Pentomino Pieces Calendar Puzzle
The shaped tiles you place on the board. Inspired by the DragonFjord A-Puzzle-A-Day, you must arrange them to leave only today's date uncovered.
